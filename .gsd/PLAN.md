## Current milestone: P1 Persistence with SQLite (M0 to M4a, L1, A1, L2 and A1b complete)

Order of work: **P1** (SQLite persistence: a contract fix and a guard first, then the adapter, durability, the capture flow on it, the explorer, a benchmark, and optional export/import) → then choose from the Later milestones. SQL push-down for set queries and `data` matching arrives with M4b, because the core does not issue those queries yet.

## U1 User accounts and login API (roadmap item 2; starts with T-069)
Decisions (owner, 2026-10-05): password plus **server-side sessions**; **open self-registration**; **one graph per user**, its id derived from the user id and never taken from a client; a new component `src/users/` (logic over SQLite, no HTTP) and a thin **HTTP API** on `node:http`; no new dependency (`node:crypto` scrypt for passwords). Proposed, to confirm in T-069: the first account created becomes the admin; roles are only `user` and `admin`; the "details" of a user are username, display name, optional email (never verified or mailed: the Pi has no outbound mail) and timestamps; no password-reset email (an admin resets passwords); registration can be switched off by configuration. Open registration makes throttling and the account-enumeration rules part of the work, not an extra.
- [ ] T-080 (R-002) HTTP server kit for the API — acceptance: new component `src/api/` (tenth entry point if exported, boundary-tested; the only place besides the dev kit allowed to import `node:http`), built on `node:http`, no dependency: bind address configurable and **defaulting to 127.0.0.1**, JSON only (`application/json` required on bodies, 415 otherwise), body limit 16 KB (413), header and request time limits, `Origin` check on every non-GET request (cross-origin is 403, the dev kit's rule), cookie parse and serialise (`HttpOnly`, `SameSite=Strict`, `Path=/`, `Secure` when configured), security headers on every reply (`Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'`), uniform JSON errors with no stack or internal message, unknown routes 404 and wrong methods 405 with `Allow`, a hostile-input battery (huge headers, invalid JSON, prototype keys, bad cookies, path tricks); mutation-checked
- [ ] T-081 (R-002) Account routes — acceptance: `POST /api/register`, `POST /api/login` (sets the session cookie, body never contains the token), `POST /api/logout` (clears it), `GET /api/me`, `PATCH /api/me`, `POST /api/me/password`, `DELETE /api/me` (body carries the password), and admin routes `GET /api/users`, `GET|PATCH|DELETE /api/users/:id`, `POST /api/users/:id/password`; statuses mapped from `UsersError` (401, 403, 404, 409, 422, 429 with `Retry-After`); the session cookie is the only credential (an `Authorization` header is ignored); a test walks every route over real HTTP with and without a session and as each role; **no response, log line or error ever contains a password, a hash or a token** (scanned across the whole test run); logging of requests excludes bodies and cookies; mutation-checked
- [ ] T-082 (R-002) Run it: configuration, entry point, recovery command, docs — acceptance: `npm run users -- recover-admin <username>` (UA-FR-13) reads a new password from standard input, sets it for that admin account only, ends that account's sessions, and refuses a username that is not an admin; `npm run serve` (outside the gate) starts the API from environment variables (`CACI_PORT`, `CACI_BIND`, `CACI_DATA_DIR`, `CACI_ALLOW_REGISTRATION`, `CACI_COOKIE_SECURE`, `CACI_TRUST_PROXY`), creates the data directory owner-only, opens the graph and user databases, closes both on SIGINT/SIGTERM, refuses an invalid configuration with a message naming the variable, and refuses to bind a non-loopback address with `Secure` cookies off unless told to explicitly; README gains **User accounts and the login API** (what exists, the routes, the cookie, the password rules, throttling, that email is not verified or sent, how an admin resets a password, that the first account is the admin, backup of two files, **HTTPS is not terminated here: use a reverse proxy**, and what is not protected); a smoke test starts it on port 0 against temp files
- [ ] T-083 (R-002) End to end and review — acceptance: one test walks the real stack over HTTP and real SQLite files: register the first user (admin), register a second, each logs in, each gets a different graph id from `/api/me`, the second cannot see or change the first's account or graph, an admin lists both, resets the second's password (old password and old sessions stop working, the new one works), the second deletes their account (their graph is gone, the other's is intact), restart the server on the same files and the first user's session cookie still works; a written security review in the spec marks each threat from T-069 with the test that covers it, and anything uncovered becomes a Backlog item with a reason

## Backlog
- Explorer UI is verified by hand in Chrome only. A hidden or background browser tab throttles timers and never fires `requestAnimationFrame`, so scripted checks should wait on server round trips, not timers. If the UI keeps growing, consider a small browser-level test (for example Playwright) as a dev-only dependency.
- **Measured (T-066, 2026-10-06, SQLite on a file, Node 22.19, this laptop):** reaching page 100 of the 5,000-item category costs about the same as its first page (p95 107 ms against 102 ms), so skipping to a cursor is **not** the problem; the cost is that a query from a category with depth 1 reads **the whole category's edges (and then its items) before it pages**, so the first page of a 5,000-item category takes about 100 ms whatever the page size. Ordinary categories are fine (random category, page of 50: p50 8.5 ms, p95 14.8 ms, under the 20 ms target). Decide on evidence whether it matters: a push-down or a streaming executor for single-seed depth-1 queries, or cursors that carry the adapter's own cursor so a page reads only what it needs. Not urgent for a household-sized graph.
- Privacy before real use of the LLM (T-047 onward): captured text is sent to an external model. Decide whether a redaction step is needed and what must never be sent; the `ModelClient` port keeps a local model possible later. Not answered yet.
- Packaging: `src/llm/` and `src/app/` currently ship as entry points of one package whose name says "bipartite-graph". Decide at M7 whether the platform becomes a workspace of separate packages.
- Preview is computed by the controller from the proposed mutation and the current graph. If it ever needs to be exact (what `write` would really do), add a dry-run option to `write` that applies in a transaction and rolls back.
- Explorer follow-ups (optional): a step-back/undo for scenarios. The page has no browser-level automated test; the server, layout logic and release guards are tested and the UI was checked by hand in Chrome.
- **Measured (T-066):** `describeGraph` on 10,000 items, 1,000 categories and 100,000 edges takes about 525 ms (p95 571 ms) on SQLite, because it walks the whole graph in one transaction (O(n); writers wait). Fine for a rare call; if it is shown in a UI on every load, add the optional adapter fast path (`count()` under `capabilities`, SQLite `COUNT(*)`).
- Known limitation of `createIfMissing` (narrowed by T-059, which makes creation atomic and tells `write` whether it created the graph): a concurrent writer that sees a graph that a failed call then removes gets a `STORAGE_ERROR`. A fully clean fix is an adapter-level "create graph and run transaction" primitive; low risk for a single-process proof of concept, so it stays here.
- Consider rewording AC-03 in the R-001 spec: in the v1 format a link has one `item` and one `category` field, so item–item and category–category edges are unrepresentable; the AC is satisfied by the format plus strict validation rather than by a dedicated check.

The preview now covers it (T-046 warns about such links); a `knownCategoryIds` option so the repair attempt could fix it is still open and can wait for the evaluation (T-048).
- A failed `categorise` call returns an error with no token usage, so tokens spent on a rejected attempt are not reported (matters for cost tracking in the lab and T-048). Consider adding `usage` to `LlmError` or a result wrapper.

- **Optimisation idea (deferred by the owner, 2026-10-04): a Jev classifier path.** TypeSafe's Jev is a "System One" model: one call to `POST https://api.typesafe.ai/v1/systemone` (bearer key) takes a `state` (the note) and typed questions (`choice` over up to 255 options with probabilities and confidence, `noul` yes/no probability, `score` 2 to 10 levels) and returns typed answers, no generated text; questions run in parallel; about $0.042 per million input tokens, 64k context, about 80 requests per second; not trained on customer data, zero retention enterprise-only; English best (docs: https://docs.typesafe.ai/). Fit: choosing among *existing* categories (a `choice` for the top pick or a `noul` per category for several, with calibrated confidence for the preview), and safer because the model can only return probabilities for ids we send, so a note cannot make it emit an operation. Does not fit: inventing new categories or writing an item title and summary, and it is not a `ModelClient` (it needs its own classifier port, with its own contract suite and a plain-HTTP client, so no new dependency). Proposed shape when revisited: Jev first to match existing categories (deterministic title and summary), escalate to the frontier `categorise()` when Jev says none fit or its confidence is low; compare Jev with the Anthropic tiers on a golden set in T-048 before wiring anything. Open points: quality on real notes is unmeasured (speed and cost figures are the vendor's), more than 255 categories need a pre-filter or one question per category, and it would be a second vendor receiving notes (extends the privacy question above). First step if picked up: a `jev:try` spike outside the gate, with the owner's key from the shell environment, never a file in the repo.
- **Privacy milestone (deferred by the owner, 2026-10-04): pseudonymise notes before they go to a model.** Needed before anyone's data other than the owner's is used, or before this stops being a personal proof of concept. Encryption cannot help at the model (it must read plaintext; homomorphic encryption is impractical for LLMs; confidential computing would need provider support, which I am not aware the Anthropic API offers; ask them), so the plan is pseudonymisation: a pure step in `src/app/` between the normaliser and `categorise`, so the LLM component is unchanged. Shape: `pseudonymise(note, categories)` returns tokenised text and context plus a mapping (`Dr Patel` to `PERSON_1`); `restore(proposal, mapping)` runs before the preview and rejects an unknown token or a leaked raw identifier; the mapping lives only as long as the pending proposal, is never sent, and any stored alias table is encrypted at rest. Decisions to make then: per-note tokens (more private, probably enough) versus stable aliases (the provider could link notes); detection by the owner's own contact list plus patterns (emails, phones, addresses, account numbers, dates of birth) first and an optional local detection model later; category names and data are part of what is sent and must be tokenised too; a preview of the exact outgoing text and a confirmation when something looks like PII but is unmapped (fail closed); the controller must also keep restored names out of anything sent on a later call. Test idea: the scripted client records every outgoing request, so a test can assert that no registered identifier appears in any of them; the lab can show the outgoing text. Limits to remember: it is pseudonymisation, not anonymisation (still personal data in law while re-identification is possible), indirect identifiers and health content remain sensitive, and a detector will miss things. Also decide then: a data processing agreement, retention and region terms with the provider, a local-model option for sensitive notes, and whether this is personal-use only (lighter obligations, but take legal advice) or a service for others (lawful basis, a risk assessment, a contract).
- Strengthen the evaluation before trusting the default tier: re-run with `--repeat 3` for variance; add harder and more ambiguous notes to the golden set (the first real run left fast and balanced both at 100%, so it cannot separate them); put some of the owner's own notes in a local `--golden` file outside the tracked files; and add a way to judge *quality*, not only allowed behaviour (for example the model's category choice compared with the owner's own labels, or a second model as judge). Also reconsider the `empty-graph` limit of 2 new categories, which penalised a reasonable 3-category answer from deep.

- Link counts per category with SQLite (`GROUP BY` on the edge index) would make the "rank categories when more than 500 exist" item cheap; it needs a counting primitive or a `count` query per category, so decide after the T-066 numbers.

- **Product roadmap (added by the owner, 2026-10-05; to be planned later with `/plan`, in no fixed order).** None of these is specified yet: the R-001 spec covers the graph store only, and `spec.md` names just one controller. Each needs a spec section before it is planned.
  1. **CaCi controller.** The business coordination between the API, the LLM and the brain graph, and between the user and circle controllers. Today `src/app/` holds only the capture controller (propose, preview, approve, reject over one graph); this item is the platform-level coordinator it would grow into or sit beneath. Open: where the boundary is between it and the capture controller, and whether it exposes the HTTP API the PWA needs (nothing like that exists yet; the explorer and lab are dev-only and never deployed).
  2. **User controller.** (Planned as milestone U1, T-069 to T-083, on 2026-10-05.) Handling of user accounts. Open: how a user relates to graphs (a graph per user? the graph ids are lowercase and filename-safe, which suits a per-user id), authentication and sessions, storage of accounts (SQLite is planned in P1), and what a user may see and change.
  3. **Circle controller.** Handling of support circles. "Support circle" is not defined anywhere in the repository yet: before planning, define what a circle is, who belongs to it and in what roles, what of a person's graph a circle may see or change, and how consent is given and withdrawn. This is the item where **other people's data enters the system**, so it makes the pseudonymisation milestone and the legal questions (a data processing agreement, lawful basis, a risk assessment) a prerequisite, not an option, and ends the proof-of-concept scope of "the owner's own data only".
  4. **PWA.** A web app implementing the user interface in place of a full native app for the proof of concept. It needs a real, authenticated API server (see item 1), which does not exist yet, plus the capture, preview and approve flow already built as a controller; the explorer's ghost preview is the closest existing design. Open: offline behaviour, installability, and how a model key is kept server-side (it must never reach the browser).
  5. **Deploy to a Raspberry Pi** as a service for local use in the house. Depends on P1 (SQLite for durable storage; `node:sqlite` needs Node 22.13 or later, which must be available on the Pi's OS) and on items 1, 2 and 4. Open: running as a service (for example systemd) and restarting after power loss, HTTPS and access only from the home network, backups (copy the database after a clean close, or the export in T-067), updates, and that the model calls still leave the house for Anthropic unless a local model is used (running one on a Pi is unlikely to be practical).
