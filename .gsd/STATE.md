## Decisions
- 2026-10-01 — Schema validator is **Zod** — largest ecosystem, one runtime dep per NFR-03, JSON Schema derivable.
- 2026-10-01 — Toolchain is **npm + Vitest + ESLint (flat config) + `tsc --noEmit`** — gate commands to be written into system_prompt.md in T-003.
- 2026-10-01 — `link` **fails on missing endpoints by default**; `ensureNodes: true` opts in — strict and explicit, as in the spec.
- 2026-10-01 — **Lean v1**: `requestId` accepted in the schema but not implemented (no replay); caller-supplied ids only; strict bipartite, no category hierarchy.
- 2026-10-01 — **TypeScript pinned to `~6.0`** (T-002 had installed 7.0) — `typescript-eslint` peer range is `<6.1.0`; revisit when it supports 7.
- 2026-10-01 — Schemas use **strict objects** (unknown keys rejected) so typos in LLM-written instructions fail loudly; `version` is a literal checked separately for `UNSUPPORTED_VERSION` in T-008.
- 2026-10-01 — Query schema has **no `kind` field** (spec examples omit it); a mutation sent to it fails on unknown keys. `where` keys must be `data.<path>`.
- 2026-10-01 — Parsers check wrong-endpoint input before `version`, and report only the first Zod issue (one `path` per `GraphError`). All parse paths run inside a `guarded()` wrapper so hostile input cannot throw.
- 2026-10-01 — JSON Schema uses Zod 4 built-in `z.toJSONSchema` (draft 2020-12, `io: 'input'` so defaults are optional); generated files are committed and a drift test fails if they are stale. `ajv` is a dev-only dependency for tests.
- 2026-10-01 — Limits (NFR-06) are enforced in the parsers via an optional `{ limits }` argument, not in the static schema; `data` size is measured in UTF-8 bytes; op count is checked on raw input before the schema parse; limits also apply to query ids.
- 2026-10-01 — Supporting adapter types are our own definitions (spec leaves them open): `Paged<T>` = `{ items, nextCursor }`, `NodeRecord` = `{ partition, id, data? }`, `EdgeRecord` = `{ item, category, weight?, data? }`, `SetClause` = `{ all?, any?, none? }`. `AdapterTx` is scoped to one graph by `transaction(graphId, …)`.
- 2026-10-01 — Endpoint stubs return `STORAGE_ERROR` "not implemented" for valid input (error enum is closed, nothing fits better); `WriteOutput`/`QueryOutput` are placeholders until M2/M4.
- 2026-10-01 — Public instruction types (`Mutation`, `Op`, `Query`, …) are hand-written in `src/graph_store/types.ts` so the API report records their shape; `types.test.ts` asserts mutual assignability with the Zod-inferred `Parsed*` types. Changing a schema means updating both.
- 2026-10-01 — API Extractor (`npm run api` to update the report, `api:check` is part of the gate) bundles TS 5.9 and warns about TS 6.0; output is still correct. Purity (NFR-02) is a lint rule on `src/**` non-test files plus a test that proves the rule fires.
- 2026-10-01 — **Graph store isolation**: everything lives in `src/graph_store/` (user decision, matches the container diagram); package entry points build to `dist/graph_store/`; generated JSON Schema moved to `schema/graph_store/` and `$id` now ends `/schema/graph_store/<name>.v1.schema.json`. Public API report unchanged by the move. Test map is in the R-001 spec.
- 2026-10-01 — Memory adapter: transactions work on a shallow copy of one graph and swap on success; a per-graph promise queue serialises transactions, `create` and `drop` (no lost updates); node data is deep-copied in and out; `graphs.create` and `graphs.drop` are idempotent (spec silent; conformance suite in M3 should state this); keyset cursor is the base64url of the last key, ordering is UTF-16 code-unit order.
- 2026-10-01 — Adapters are deliberately dumb about integrity: the memory adapter does not check that edge endpoints exist and `deleteNodes` does not remove edges; the core must cascade using `edgesOf` + `deleteEdges` + `deleteNodes` in one transaction (FR-07). `putEdges` replaces the whole edge record. Conformance suite (M3) must encode this.
- 2026-10-01 — Write is built as functional core + imperative shell: `planGraphResolution` is pure, `resolveGraph` does the I/O and returns `{ created }`. Public `write()` stays a stub until T-019 wires everything, so no half-applied mutation is ever observable. Adapter failures map to `STORAGE_ERROR` via a shared `storageError` helper.
- 2026-10-01 — Node ops (T-017): `upsertNode` `replace` sets data to exactly the op data (omitted data clears it, PUT semantics) — PROVISIONAL, see Blockers; `merge` is shallow (op keys win, `null` overwrites, nested objects replaced); `deleteNode` removes the node's edges page by page (1000 per page) then the node, and is a no-op for a missing node (idempotent, no `NODE_NOT_FOUND`).
- 2026-10-01 — Link ops (T-018): `link` replaces the whole edge (an omitted weight/data clears the old one; same PUT semantics as upsertNode `replace`, follows that provisional decision); `unlink` of a missing edge or nodes is a no-op; `NODE_NOT_FOUND` reports the item first and its path is relative to the op (runner prefixes `['ops', i]`). AC-03 holds by construction (the format has one `item` and one `category` field) and is proven by parser tests rather than a runtime check.
- 2026-10-01 — Atomic write (T-019): a failing op throws inside the transaction so the adapter rolls back; errors get an `['ops', i]` path prefix. A graph created by a failed call is dropped only if still empty (protects a concurrent writer; a small race remains, see PLAN Backlog). Adapters reporting `transactions: false` are refused with `STORAGE_ERROR`. `WriteOutput` = `{ graphId, applied, graphCreated }`; API report re-baselined for it.
- 2026-10-01 — **FR-01 graph lifecycle (user decision, option 2)**: graphs are managed by four top-level functions beside the two endpoints — `createGraph`, `dropGraph`, `listGraphs`, `describeGraph` — not by extra ops in the mutation/query formats. This widens the public API deliberately; the v1 mutation and query schemas stay unchanged. Planned as M2b (T-024 to T-026), scheduled before the conformance suite so M3 can include lifecycle behaviour. Proposed semantics, to confirm: `createGraph` on an existing graph gives `CONFLICT` (whereas `createIfMissing` in `write` stays idempotent); `dropGraph`/`describeGraph` on a missing graph give `GRAPH_NOT_FOUND`; `describeGraph` returns `{ graphId, itemCount, categoryCount, edgeCount }`, counted by paging (O(n) in v1).
- 2026-10-01 — Lifecycle (T-024): the confirmed semantics are implemented — `createGraph` on an existing graph gives `CONFLICT`, `dropGraph` on a missing graph gives `GRAPH_NOT_FOUND`, graph ids are validated (non-empty string, within the id length limit) before any adapter call. Known race: existence check and create are two adapter calls (see PLAN Backlog, wants an atomic create-if-absent primitive).

- 2026-10-02 — **Graph ids restricted (user decision, T-029)**: a `graphId` is 1 to 128 characters of `[a-z0-9_-]`, starting with a letter or digit, enforced in both schemas (and so in the published JSON Schema, which now carries the pattern), `createGraph`, `dropGraph` and `describeGraph`, always before any adapter call. Reason: graph ids become file names and keys; lowercase-only also removes case-collision on case-insensitive file systems (macOS, Windows). Strict first on purpose: loosening later is non-breaking, tightening is not. - 2026-10-02 — Query results and cursors (T-031): four result shapes as explicit public types (`nodes`, `ids`, `count`, `subgraph`), told apart by their keys; no tag field, so the spec's JSON is unchanged. One fixed order: items then categories, each by id in UTF-16 order. `page.limit` counts nodes; in a `subgraph` each edge travels with its item end and only if its category end is in the whole result, so a page can carry more edges than `limit`. `truncated` means a size cap cut the result (reached-node cap, default 10,000; implemented in T-034), never paging. Edge `weight` is always reported (1 when none is stored, as the spec's example shows); `data` follows `includeData`, default false (provisional). Cursors are opaque, versioned, checksummed and bound to a fingerprint of the query (everything except `page`), so a cursor from another query, or a corrupted or edited one, is a `VALIDATION_ERROR` at `page.cursor`.
- 2026-10-02 — Query planner (T-032): `planQuery` is pure and internal. It refuses features that the schema accepts but nothing executes yet — `from.where`, `filter.where`, and the `all`/`any`/`none` clauses, **including empty ones** (an empty set clause is not read as "no constraint", because the spec does not say what it means and a wrong guess gives answers that look right) — with `VALIDATION_ERROR` "not supported yet" and a path, in the fixed order from.where, filter.where, all, any, none; M4b removes these refusals. `from: all` ignores `traverse` (plan depth 0). Seed ids are de-duplicated and ordered. A cursor on a `count` is refused (a count is not paged). `excludeSeeds` on `from: all` is passed through (the result is empty).
- 2026-10-02 — Read executor (T-033): `executePlan` reads only through a frozen handle with `getNodes`, `listNodes` and `edgesOf` (no write methods exist on it); the shell `executeQuery` checks the graph exists (`GRAPH_NOT_FOUND`), runs inside one adapter transaction and turns any failure into `STORAGE_ERROR`. Handles `from: all` and named seeds at depth 0, the partition filter, `nodes`/`ids`/`count`, `includeData` and paging. Paging is by position: the executor skips adapter pages until it passes the cursor's node (correct and stable, but each page costs more the further in it is; see Backlog). Depth above 0 and `subgraph` are refused by name until T-034/T-035, so named seeds currently need an explicit `depth: 0`. `Limits` gained `maxReachedNodes` (default 10,000): `count` stops there as a lower bound, and named seeds beyond it are cut and marked `truncated`. The executor stops with `STORAGE_ERROR` when an adapter's cursor does not advance, instead of looping.
- 2026-10-02 — Traversal (T-034): breadth-first from the named seeds, `depth` hops, each hop crossing to the other partition; the result is cumulative (everything within the depth, seeds included) with each node once. The spec's sentence about hops was ambiguous ("depth 2 [from a category] gives items sharing a category"); by its own rule that each hop flips partition, that is depth 3 from a category or depth 2 from an item, so the unambiguous flip rule is implemented and the spec sentence and the T-034 plan text were corrected. `excludeSeeds` drops the seeds but keeps what they led to; the partition filter narrows the reached set after the walk (the walk still passes through the other kind). The reached-node cap stops the walk, including partway through a hub's edge listing (a 5,000-item hub with cap 100 takes at most 2 edge-page reads), and sets `truncated`; which nodes survive a cut is deterministic. An edge to a node that is gone is skipped. Cycles cannot loop (depth is at most 3 and results are keyed). `subgraph` is still refused until T-035.
- 2026-10-02 — Subgraph shape (T-035): the executor now handles all four shapes. A page's edges are those of its item nodes whose category end is also in the whole result (named seeds: the reached set after `excludeSeeds` and the partition filter; whole graph: the category exists, and no edges at all under a partition filter), so each edge appears once, on its item's page, and a page can carry more edges than `limit`. Edges are ordered by item then category. Weight is always reported (1 when none stored, a stored 0 kept); edge `data` follows `includeData`. A page carries at most `maxReachedNodes` edges (default 10,000, the same limit as reached nodes) and is marked `truncated` beyond that, so one item with a huge edge list cannot exhaust memory. The executor now refuses nothing; the planner still refuses data matching and set clauses until M4b. `query()` itself is still a stub until T-036.
- 2026-10-02 — `query()` wired (T-036): parse, plan, execute, with every refusal returned as a result before the adapter is touched (proved with an adapter that records any property read, across 17 invalid inputs). Options: `write`, `query`, `createGraph`, `dropGraph`, `describeGraph` and `createGraphClient` take an optional `GraphOptions` (**renamed from `ParseOptions`**, since it now configures reads, writes and graph ids). Only `limits` exists (maxOps, maxDataBytes, maxIdLength, maxReachedNodes); it is validated strictly — unknown options or limit names and non-positive-integer values are `VALIDATION_ERROR` with an `options` path before the adapter is touched, and `createGraphClient` throws `RangeError` for them since that is a coding mistake, not a request. A client keeps its own frozen copy of its options. `listGraphs` takes no options (it validates a page, not ids). The placeholder `QueryOutput` and the "decide how options reach the endpoints" Backlog item are gone.
- 2026-10-02 — Reads group (T-037): the shared suite now holds `query()` end to end (17 cases: AC-09, 13, 17, 19, 21, 22 plus FR-14 paging, seeds, filters, caps, isolation), built only from the public `write`/`query` with adapter primitives used solely to prove the store unchanged. - 2026-10-03 — Model tiers and routing (T-051): `createLlmConfig` and `resolveModel` in `src/llm/config.ts`, pure and never throwing. Tiers `fast` = `claude-haiku-4-5-20251001`, `balanced` = `claude-sonnet-5-5`, `deep` = `claude-opus-5-5`, all overridable; `categorise` routes to `fast` by default (provisional until the T-048 evaluation). A capability route is an object, `{ tier }` or `{ model }` (never a bare string, so a typo like "fats" is an error rather than a model id) with exactly one of the two. Model ids are checked loosely (non-empty, at most 200 characters, no whitespace or control characters) because providers write them very differently. A new boundary test fails if the LLM component reads `process.env`, `process.argv` or files: the app and dev tools read the environment and pass the result in. Configs are frozen and independent of the caller's input object.

- 2026-10-06 — Password hashing (T-072): `createPasswordHasher({ params?, randomBytes?, derive? })` in `src/users/password.ts` (public: `createPasswordHasher`, `DEFAULT_SCRYPT`, the types), scrypt from `node:crypto`, asynchronous so the event loop is not blocked, no dependency. - 2026-10-06 — Throttling (T-076): `src/users/throttle.ts`, pure and clock-injected (time is an argument; the only state is the throttle's own bounded memory). **`createLoginThrottle`** (`check`, `recordFailure`, `recordSuccess`, `purge`, `size`): two keys, the normalised username (lower-cased, cut at 128 characters) and the client key the caller supplies. Per username: after 5 failures the next attempt is held back 1 s, then 2 s, 4 s, 8 s ... capped at 15 minutes, measured from the last failure; a failure older than 15 minutes starts the count again; a success clears that username. Per client, over all usernames: the same shape but 20 failures (a household shares an address), and a success does **not** forgive the client. `check` takes the longer of the two waits and **changes nothing**, so a caller that checks first and does not record throttled attempts cannot make a hold longer by hammering (the controller must do exactly that: check, refuse with `throttledError(retryAfterMs)`, record only real attempts). The throttle never sees the user store, so an unknown username is held back exactly like a real one provided the controller records failures for both (tested with 6 odd usernames: empty, spaces, path-like, NUL, 10,000 characters, non-Latin). **Bounded memory**: each table keeps at most `maxEntries` (10,000), and when full makes room in the order: an entry past its window, then one that never reached the threshold, then the oldest, so a flood of made-up names cannot push a lock that is really holding someone back out (tested: 2,000 made-up names against a table of 20). **`createRegistrationThrottle`**: 10 attempts an hour per client, sliding, `retryAfterMs` counted from the oldest attempt that counts; keeps only the latest `max` attempts per client (a test found the wait would be wrong if it kept more), at most `maxEntries` clients. **`throttledError(ms)`** is the `THROTTLED` error, rounded up to whole seconds, saying nothing about which key was over. Settings validated with `TypeError`. 27 tests; 29 deliberate defects, one survivor (the per-client attempt list was unbounded and the wait wrong) got a test. **Known limits, stated honestly**: (1) throttling by username lets an attacker who knows a username keep that account held back (up to 15 minutes at a time) by failing on purpose: the price of not revealing accounts; the owner can still log in from nowhere else during a hold, so an admin's account is the one to watch; recorded in the Backlog; (2) a distributed attacker using many client keys evades the per-client limit, and many usernames evade the per-username one: that is what password policy and scrypt cost are for; (3) the state is in memory, so a restart forgets it (acceptable for a household service, noted for the Pi item); (4) the client key is whatever the API passes (the socket address, or a trusted proxy header only when configured: T-080 and T-082).

## Blockers / open questions
- Privacy: captured text goes to an external model (Anthropic). Accepted for the proof of concept, which holds only the owner's own data. A pseudonymisation milestone is in the PLAN Backlog and must be reopened before anyone else's data is used or the tool is offered to others.
- Model defaults: `categorise` runs on the `fast` tier (Haiku 4.5); a first real evaluation supports it (see the decision log) but is a small sample. Heavier future capabilities default to `deep` (Opus 5.5) and are untested. Override per capability, per call or per run in the lab.
- Confirm `upsertNode` `replace` semantics: with no `data` it currently clears existing data. Alternative: omitted `data` leaves existing data untouched in `replace` mode. Spec says the default must never change within a major version, so settle before 1.0.0. Not blocking T-018 to T-022.
- Remaining open question from R-001 spec: expected scale per graph and number of graphs (confirms NFR-05 targets); not blocking until M6.
